# Benchmark 验证记录

日期：2026-10-26。运行环境：macOS 本地机器，Intel Core i5-1038NG7（8 线程），Python 3.12.13，
OR-Tools 9.15.6755。机器未独占（测试期间 load average 约 4–5），不能外推为生产性能承诺。
当前依赖由 uv.lock 管理。

41 项 pytest 回归测试通过，包括一次卸货、同站时间窗交集、同站分车、
三种计数口径、四舍五入、开放路线、非嵌套车型容量、两种目标、硬距离约束、
首段关联约束、时间窗异常、禁用时间窗、矩阵错误、无订单、精度拒绝、限时兜底和可视化。

合成规模：100 DN、6 车型、maxSiteQty=5、站间距离上限40、首段关联约束开启、时间窗10:00–18:00、
`quotationModel=city`（车辆数优先）。每个 DN 体积1、重量100、不同站点。
种子 0–4，矩阵预生成，不含网络或 JSON 解析。按 maxSiteQty 计，车辆数下限为 20。

## 路线消除阶段（车辆数优先）

同一台机器连续运行，合成 100 DN，种子 0–7，改动前后对比（`quotationModel=city`）：

| 预算 | 平均车辆数 前 → 后 | 平均距离 前 → 后 | 耗时中位 / 最大 后 |
|---:|---|---|---|
| 200ms | 22.12 → 21.62 | 1836 → 1841 | 221 / 242ms |
| 1000ms | 22.00 → 21.25 | 1639 → 1736 | 1007 / 1019ms |
| 3000ms | 22.00 → 21.12 | 1557 → 1591 | 3012 / 3022ms |

- 车辆数减少 0.5–0.9 辆；距离是代价，符合“车辆数优先于距离”的目标。
- 阶段预算为总预算的 25%，达到下界或连续失败 200 轮即提前结束。
- 偏距离模式不启用该阶段。该模式 200ms / 1000ms 下仍多为插入兜底，且耗时明显超出预算
  （最大 0.8–1.2s），偶发 40+ 车的结果；前后版本都存在，是另一个待处理的性能问题。
- 仅 8 个合成样本，计时受机器负载影响，不能外推为生产指标。

原先距离优先按每车型 N 个槽位建模（共 600 个），改为与车辆数优先一致、按初解路线数预留：

| 预算 | 每车型槽位 | 平均建模 | 平均距离 | 来源 |
|---:|---|---:|---:|---|

## 首段约束改为预算维度（2026-10-27）

首段约束原先用 `solver.Element` + `solver.Add` 表达，局部搜索过滤器看不到它：
OR-Tools 插入类算子（`filter_with_cp_solver=false`）产生的候选能通过全部过滤器，
却在最终 CP 检查中被否决（剖析中整路线重插算子通过过滤 32–44 次、接受 0 次）。
现改为负增量的 `FirstLeg` 维度：出仓存入首段距离，每段站间距离扣减，余额不得为负；
同时删掉只为它服务的 `Distance` 维度。

同一台机器先后运行，合成 100 DN、6 车型：

| 场景 | 预算 | 平均车辆数 前 → 后 | 平均距离 前 → 后 |
|---|---:|---|---|
| 车辆数优先完整流程（种子 0–7） | 200ms | 21.625 → 21.625 | 1840.6 → 1840.6 |
| 车辆数优先完整流程（种子 0–7） | 1000ms | 21.375 → 21.125 | 1775.7 → 1589.3 |
| 车辆数优先完整流程（种子 0–7） | 3000ms | 21.125 → 21.125 | 1613.1 → 1566.1 |
| 车辆数优先、仅 OR-Tools（种子 0–7） | 3000ms | 22.0 → 22.0 | 1548.5 → 1542.3 |
| 距离优先（种子 0–4） | 1000ms | 26.6 → 26.6 | 1352.2 → 1350.6 |
| 距离优先（种子 0–4） | 3000ms | 26.6 → 26.6 | 1350.6 → 1348.7 |

- 主要收益是距离：拆车阶段为减车牺牲的距离，OR-Tools 现在能修回来更多（1 秒约 −10.5%，3 秒约 −2.9%）。
- 仅靠 OR-Tools 仍然减不了车：本数据 maxSiteQty=5、路线几乎满载，整路线重插找不到空位；
  腾挪空位仍依赖拆车阶段的抖动。
- 200ms 下不进入搜索，结果相同。旧版本 200ms 一轮运行时机器上同时跑了测试，耗时不可比。

## 插入阶段去掉 40ms 上限（2026-10-28）

插入阶段原先取“总预算 20%”与 40ms 的较小值。40ms 恰好等于默认 200ms 预算的 20%，
所以只在更大预算下生效。插入只扫一遍，截断后剩余 DN 改为直送，车辆数后续几乎减不回来；
直送路线多又会放大 OR-Tools 的槽位数，拖慢建模。现只保留 20% 的比例。

同一台机器先后运行，合成 300 DN、6 车型，其余配置同上，种子 0–4。
不限时运行插入法约需 150–250ms，得到 60–62 辆车。

| 模式 | 预算 | 平均车辆数 前 → 后 | 平均距离 前 → 后 | 耗时中位 前 → 后 |
|---|---:|---|---|---|
| 车辆数优先 | 1000ms | 300 → 287.4 | 11588 → 11204 | 2940 → 1492ms |
| 车辆数优先 | 3000ms | 188.8 → 60.6 | 8077 → 4554 | 3607 → 3159ms |
| 距离优先 | 1000ms | 300 → 230.6 | 11588 → 9194 | 2078 → 1449ms |
| 距离优先 | 3000ms | 252.8 → 67.6 | 9950 → 3562 | 12791 → 3088ms |

- 3000ms 下插入能跑完，车辆数降到 60–69，接近 maxSiteQty 下限 60；
  旧版距离优先因直送路线多、槽位多，建模 9–17s，严重超出预算。
- 1000ms 下多数样本仍是直送兜底：300 DN 的输入校验和预处理本身约需 1s，
  进入初解阶段前预算已用完。这是另一个待处理的性能问题。
- 前一轮运行时机器负载更高（不限时插入耗时约为后一轮的 2 倍），耗时列只看量级。
